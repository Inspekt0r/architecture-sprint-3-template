Задание 2

Итак перейдем к решению наших проблем.

т.к. у нас разработчики изначально писали всё на Java SpringBoot, то мы ничего менять не будем.

наши DevOps инженеры настроят классный пайп CI/CD с использованием k8s+helm+Jenkins

Добавим кафка шину для обмена данными между микросервисами, это даст возможность нам сделать систему:

1) масштабируемой
2) отказоустойчивой

Касательно асинхронщины в гейтвее на авторизацию: сделал так во избежание если гейтвей станет узким горлом, мы всегда
легко его отмасштабируем

Также помимо этого решил добавить адаптер для устройств, дабы сервис работал с понятными данными и не был перегружен
логикой
мапинга, а также разными протоколами общения с устройствами.

В остальном придерживаемся парадигмы One Service - One database.

Единое фронтенд приложение т.к. сейчас микрофронтенд будет больше во вред и тормозить распил основного монолита.
В будущем всегда можно будет сделать 3 микрофронта для пользователя, админа и саппорта.

Для бэкенда также можно в будущем добавить BillingService для оплаты подписки на наш сервис клиентами.
BillingService будет связан с внешними платежными системами. Но на данный момент такой задачи не стоит, это мысли в
слух.

Касательно сущностей мы изменим старые и добавим новые сущности.
User, Home, Device, TelemetryData

Почему в Device нет isOn, currentTemperature и т.д. параметров? Ответ прост: я их убрал.)
На самом деле по логике хранить эту информацию нет смысла т.к. у нас есть TelemetryData и в DeviceDto появляются данные
по телеметрии устройства и мы в эти поля isOn etc будем добавлять последние по времени из TelemetryData, то есть
пользователь будет видеть наиболее актуальные данные по устройству, а мы их не будем хранить в БД в сущности устройства.
А если он захочет посмотреть историчность состояния, то уже отдельно в листе данных телеметрии он сможет ознакомиться.
(например за последний час, сутки и т.д.)
Надеюсь выразился ясно.
